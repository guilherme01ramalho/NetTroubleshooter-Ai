Miniguia de Estudo de Troubleshooting de Redes para Service DeskEste guia foi elaborado para servir como material prático de estudo e consulta rápida durante o atendimento de suporte técnico. Todas as informações estão fundamentadas em diagnósticos sistemáticos e baseadas estritamente nas documentações de rede1more_horiz.1. Fundamentos EssenciaisEndereço IP: É um número de 32 bits que identifica de forma exclusiva um host (computador, impressora ou roteador) em uma rede TCP/IP ou na Internet67. Geralmente é representado no formato decimal com pontos, dividido em quatro octetos (ex: 192.168.123.132)68. Ele possui duas partes fundamentais: a identificação da rede e a identificação do host9.Máscara de Sub-rede: Também é um número de 32 bits, utilizado pelo protocolo TCP/IP para separar as porções de rede e host do endereço IP7. Ela permite ao computador determinar se um host de destino está na mesma sub-rede local ou em uma rede remota9.Gateway Padrão: É o dispositivo de rede (roteador) configurado no host que vincula a sub-rede local a outras redes10. Quando o computador identifica que o destino é um host remoto, ele encaminha o pacote de dados para o gateway padrão para que este faça o roteamento11.DNS (Sistema de Nomes de Domínio): É o protocolo padrão de camada de aplicação que mapeia nomes de computadores amigáveis para endereços IP lógicos, permitindo a resolução de nomes no Windows112. Cada conexão de rede deve possuir o IP de ao menos um servidor DNS para garantir a navegação1.DHCP (Dynamic Host Configuration Protocol): Protocolo cliente/servidor que automatiza a atribuição e o gerenciamento centralizado de endereços IP e configurações de rede (como máscara de sub-rede, gateway padrão e servidores DNS) a partir de um pool (escopo) gerenciado3more_horiz.TCP/IP: É o conjunto de protocolos, padrões e utilitários usados para a comunicação na Internet e em grandes redes7. A configuração correta do TCP/IP em um host Windows exige obrigatoriamente um endereço IP, uma máscara de sub-rede e um gateway padrão2.2. Metodologia de Diagnóstico SistemáticoO diagnóstico de redes deve seguir um fluxo lógico rigoroso para evitar conclusões precipitadas e alterações de configuração desnecessárias:$$\text{\textbf{Evidência}} \rightarrow \text{\textbf{Hipótese}} \rightarrow \text{\textbf{Teste}} \rightarrow \text{\textbf{Resultado}} \rightarrow \text{\textbf{Interpretação}} \rightarrow \text{\textbf{Próximo Teste}} \rightarrow \text{\textbf{Correção}}$$Evidência Observada: É o fato concreto relatado ou capturado (ex: o usuário não navega em um site ou o comando retorna "Request timed out")15.Hipótese: Uma suposição lógica baseada na evidência (ex: "o servidor DNS padrão pode estar inoperante")16.Teste: Ação prática e pouco invasiva executada para isolar a causa (ex: realizar um nslookup ou ping direto por IP)1617.Resultado: O retorno de dados fornecido pelo teste (ex: o nslookup retorna o IP do site com sucesso)18.Interpretação: Análise técnica do resultado do teste para validar ou descartar a hipótese (ex: se o DNS resolveu o IP, o problema não é o DNS, e sim a camada IP ou aplicação).Próximo Teste / Correção: Se a hipótese for descartada, formula-se um novo teste. Se a hipótese for validada e a causa for confirmada, aplica-se a correção definitiva (ex: redefinir as tabelas de cache DNS com /flushdns)19.3. Comandos Essenciais do WindowsipconfigPara que serve: Exibe os parâmetros básicos de configuração de rede TCP/IP ativa no computador20.O que ele testa: Verifica os endereços IPv4 e IPv6, a máscara de sub-rede e o gateway padrão de todas as interfaces físicas e lógicas2021.Exemplo: ipconfig22.Interpretação: Permite identificar rapidamente se a máquina recebeu parâmetros válidos de rede ou se está sem comunicação lógica23.ipconfig /allPara que serve: Exibe a configuração detalhada e completa de TCP/IP de todos os adaptadores de rede do sistema21.O que ele testa: Além do IP e máscara, exibe se o DHCP está habilitado, o status de concessão, o endereço MAC físico, os servidores DNS ativos e os sufixos de pesquisa DNS configurados1421.Exemplo: ipconfig /all22.Interpretação: Essencial para diagnosticar se o cliente obteve as opções de DHCP corretas (como os IPs dos servidores DNS internos)14.ipconfig /releasePara que serve: Libera e descarta a configuração IP atual obtida via DHCP24.O que ele testa: Envia uma mensagem DHCPRELEASE para o servidor DHCP, desabilitando o tráfego TCP/IP na interface selecionada24.Exemplo: ipconfig /release24.Interpretação: Utilizado antes de renovar uma concessão para garantir que o IP antigo seja totalmente descartado24.ipconfig /renewPara que serve: Força o adaptador a renegociar e renovar uma configuração de endereço IP junto ao servidor DHCP25.O que ele testa: Reinicia o processo de obtenção de concessão de parâmetros automáticos de rede25.Exemplo: ipconfig /renew25.Interpretação: Se retornar um erro de tempo limite, indica que o computador não conseguiu se comunicar com nenhum servidor DHCP ativo na sub-rede local18.ipconfig /flushdnsPara que serve: Esvazia e redefine por completo o cache de resolução do cliente DNS local19.O que ele testa: Limpa registros temporários desatualizados ou consultas negativas armazenadas em cache pelo Windows19.Exemplo: ipconfig /flushdns22.Interpretação: Resolve problemas em que um site mudou de IP, mas o computador afetado ainda tenta acessar o IP antigo armazenado localmente19.pingPara que serve: Verifica a conectividade em nível de protocolo IP direto com outro computador5.O que ele testa: Envia mensagens de solicitação de eco ICMP e calcula a latência de ida e volta5.Exemplo: ping www.microsoft.com26.Parâmetros Úteis:ping /t: Mantém o envio de pings continuamente para avaliar a estabilidade do sinal Wi-Fi ou perda de pacotes ao longo do tempo27.ping /f /l 1472: Envia pings com tamanho de pacote específico (1472 bytes de dados) e ativa o sinalizador "Não Fragmentar", ideal para diagnosticar problemas de MTU (PMTU)2829.Interpretação: Respostas bem-sucedidas indicam que a camada física e a camada de rede IP até o destino estão operacionais5. "Request timed out" indica perda do pacote ou bloqueio por firewall15.tracertPara que serve: Determina a rota lógica exata que os pacotes percorrem até alcançar um host de destino30.O que ele testa: Envia pacotes com TTL incremental para forçar os roteadores intermediários no caminho a responderem com mensagens de tempo excedido3031.Exemplo: tracert /d www.microsoft.com (o parâmetro /d acelera o teste impedindo a resolução reversa dos IPs intermediários)3233.Interpretação: Exibe cada salto (roteador) com a latência correspondente34. Uma linha cheia de asteriscos * indica que o roteador daquele salto específico está invisível ou bloqueou o tráfego ICMP31.nslookupPara que serve: Diagnostica e interroga diretamente a infraestrutura de servidores DNS35.O que ele testa: Realiza consultas de registros DNS de forma interativa ou não interativa18.Exemplo: nslookup mydomain.com 1.1.1.1 (consulta o domínio diretamente no servidor DNS público 1.1.1.1)36.Interpretação: Se retornar "Nonexistent domain", o nome pesquisado não existe na zona DNS consultada18. Se retornar "timed out", o servidor DNS configurado está inativo ou inacessível18.Test-NetConnectionNota de Grounding: Este comando do PowerShell não está presente nas fontes fornecidas neste caderno. No entanto, como boa prática de Service Desk, é importante saber que ele é utilizado no Windows para realizar testes de conectividade TCP em portas específicas de serviços (ex: testar se a porta HTTPS 443 de um servidor está aberta), indo além do simples ping ICMP. Sempre valide de forma independente o uso desse comando no PowerShell corporativo.4. Cenários Comuns de Service DeskA. Computador conectado ao Wi-Fi, mas sem InternetEvidência: Usuário conectado ao Wi-Fi local, mas nenhum site carrega.Hipótese: O computador não obteve um IP válido ou o gateway padrão está inacessível.Teste: Execute ipconfig para verificar o endereço IPv4 e o gateway padrão20.Interpretação:Se o IP for 169.254.x.x, o DHCP falhou23. Vá para o cenário de IP APIPA.Se o IP for válido (ex: 192.168.1.50), execute um ping para o IP do gateway padrão16. If o ping ao gateway falhar, a conectividade sem fio local está com problemas de sinal, isolamento de porta ou falha física no AP.Correção: reconectar ao Wi-Fi, aproximar-se do roteador ou redefinir a interface.B. Endereço IP 169.254.x.x (APIPA)Evidência: Placa de rede sem fio exibe endereço IP na faixa 169.254.x.x23.Hipótese: O computador está configurado para obter IP automático, mas não conseguiu contatar o servidor DHCP a tempo23.Teste: Execute ipconfig /release seguido de ipconfig /renew2425.Interpretação: Se o comando de renovação falhar com timeout, o servidor DHCP da rede local está travado, sem endereços livres no escopo (pool esgotado) ou há falha de broadcast físico na rede1837.Correção: Se for ambiente corporativo, verificar o status do serviço DHCP no console do Windows Server3.C. Internet funciona, mas determinado site não abreEvidência: O usuário acessa outros sites normalmente, mas um site específico exibe erro de carregamento.Hipótese: Cache DNS local corrompido ou falha no servidor DNS padrão ao resolver esse domínio específico16.Teste: Execute nslookup <site>35. Em seguida, tente nslookup <site> 8.8.8.8 (forçando o DNS do Google)36.Interpretação: Se a consulta padrão falhar mas a consulta forçada no DNS externo funcionar, o servidor DNS local está com problemas para resolver essa zona.Correção: Execute ipconfig /flushdns para limpar o cache DNS do cliente afetado1922.D. Sistema interno não abre pelo nome, mas funciona pelo IPEvidência: O usuário consegue carregar o ERP/sistema interno digitando o IP do servidor, mas não abrindo pelo nome amigável.Hipótese: Falha de resolução DNS local ou máquina configurada com servidor DNS externo público38.Teste: Execute ipconfig /all no cliente para verificar os Servidores DNS ativos21.Interpretação: Se o campo exibir DNS público (como 8.8.8.8), o computador está buscando o nome interno da empresa na Internet pública, onde ele não existe.Correção: Alterar as propriedades IP do cliente para "Obter endereço de servidor DNS automaticamente" via DHCP13 ou configurar manualmente os IPs dos servidores DNS integrados ao Active Directory corporativo139.E. Internet lentaEvidência: A navegação está lenta e intermitente, mas o gateway responde.Hipótese: Perda de pacotes na interface sem fio (Wi-Fi), gargalo no link WAN da operadora ou latência severa no DNS4041.Teste: Execute um ping persistente ping -t <IP_do_Gateway> por 15 segundos27. Em seguida, execute ping -t 8.8.8.827.Interpretação:Se o ping local ao gateway exibir perdas de pacotes ou latência instável (>100ms), a falha é no Wi-Fi (interferência de sinal).Se o ping local estiver estável (<5ms) mas o ping externo mostrar perda ou latência altíssima, há saturação ou instabilidade no link da operadora. Use o tracert -d 8.8.8.8 para rastrear o ponto de lentidão3234.Correção: Alterar o canal do Wi-Fi, migrar para cabo de rede ou acionar a operadora WAN.F. Servidor responde ao ping, mas a aplicação não abreEvidência: O ping para o IP do servidor responde perfeitamente, mas a aplicação web interna está inacessível.Hipótese: O serviço da aplicação no servidor está offline, ou as portas específicas da aplicação (ex: TCP 80 ou 443) estão bloqueadas por firewall.Teste: Testar a porta de escuta do serviço (usando PowerShell ou testando a partir de outro host na mesma rede).Interpretação: O sucesso do ping indica apenas que a conectividade básica IP existe5. Ele não garante que o serviço de aplicação ou a porta TCP correspondente estejam operacionais.Correção: Iniciar o serviço web no servidor ou liberar a porta de comunicação correspondente no firewall local/roteador de borda.G. Problemas de DNSEvidência: O usuário não navega e qualquer comando que use nomes falha38.Hipótese: Servidores DNS inativos ou inacessíveis a partir do cliente16.Teste: Execute nslookup google.com35.Interpretação: Se retornar "timed out" sucessivos, os servidores de DNS configurados não estão respondendo na porta UDP 5318.Correção: Ajustar as Opções do Servidor DHCP (Opção 006 - DNS Servers) para garantir que os clientes recebam múltiplos IPs de DNS (preferencial e alternativo) para garantir tolerância a falhas1442.H. Problemas de DHCPEvidência: Múltiplos computadores em uma sub-rede começam a receber IP APIPA23.Hipótese: O servidor DHCP parou de emitir endereços por esgotamento de escopo, travamento do serviço ou desautorização no Active Directory4344.Teste: Tentar obter IP em um host com ipconfig /renew25.Interpretação: Se a requisição expirar sem resposta, o servidor DHCP não está respondendo aos pacotes de broadcast locais.Correção: No Windows Server, reiniciar o serviço DHCP Server, autorizá-lo novamente no Active Directory ou estender a faixa de distribuição do escopo4344.5. Boas Práticas de Diagnóstico para Service DeskInvestigar do Local para o Remoto: Sempre teste a conectividade física primeiro, depois o IP local20, em seguida o gateway padrão16, para só então testar recursos externos16.Garantir Tolerância a Falhas: Ao configurar propriedades TCP/IP em clientes ou escopos de DHCP, configure sempre mais de um IP de servidor DNS, garantindo redundância de resolução caso o servidor primário falhe42.Coletar Evidências Antes de Agir: Nunca altere as configurações de IP, troque de DNS ou altere parâmetros de rede antes de rodar os testes mínimos (ipconfig20, ping5 e nslookup35) para mapear o cenário.Diferenciar Evidência de Causa: Trate o relato do usuário como evidência observada, formule as hipóteses e execute os testes para obter a causa confirmada antes de aplicar uma solução definitiva.7. Erros Comuns de Diagnóstico a EvitarAssumir que qualquer falha de Internet é DNS: Não culpe o DNS sem antes testar a conectividade IP direta enviando pings para IPs públicos conhecidos (como 8.8.8.8)16. Se o ping por IP falhar, o problema é de transporte de rede/link WAN e não de DNS.Considerar o ping como prova de que a aplicação funciona: Um ping bem-sucedido confirma apenas a resposta ICMP (Camada de Rede)5. O servidor pode responder ao ping perfeitamente mesmo com o serviço de aplicação (IIS, Apache, Banco de Dados) completamente parado ou travado.Considerar um único teste como prova absoluta da causa: Um teste isolado pode dar falsos indícios (ex: o ping para um servidor pode falhar porque ele bloqueia ICMP no firewall, mas a aplicação web continua funcionando perfeitamente). Cruze dados de diferentes ferramentas de diagnóstico.Alterar configurações antes de coletar evidências: Mudar manualmente as configurações de IP ou aplicar comandos de redefinição às pressas sem entender o erro pode mascarar o problema original, criar novos conflitos IP na sub-rede14 e dificultar o trabalho da equipe de Nível 2.Confundir causa provável com causa confirmada: Afirmar que "o problema é na operadora" antes de certificar-se de que o gateway local responde e de analisar a rota de saltos no tracert30 é um erro grave de suporte. O diagnóstico técnico de Service Desk deve se basear estritamente em dados e evidências coletadas.
